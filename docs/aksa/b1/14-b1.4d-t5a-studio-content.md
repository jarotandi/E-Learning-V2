## 5. Content state ownership (single authority)

- Canonical content owner: `useAdminContentDomain({ notify, recordAudit })`, invoked **once** by the **persistent** `AdminDashboard`.
- `AdminContentLibraryPage` is **view only** and receives `{ domain, programs }`; the two dialogs receive granular props.
- The route-mounted page does **not** hold any video/upload state and does **not** invoke its own hook.

### Why a hook, not a route-mounted page

The legacy `AdminDashboard` kept the Content Library state **above** the conditional `activeTab === 'content'` JSX, so a transient upload/editor draft survived client-side tab changes. Moving the state into a page that only mounts for `/admin/studio/content` would silently lose that behaviour. The hook is therefore invoked by the persistent orchestrator, preserving parity (proved in the browser — see §14).

### Dependency order

`notify` → `recordAudit` → `programsList` → `useAdminUsersDomain` → `useAdminQuestionsDomain` → **`useAdminContentDomain`** → consumers. Both injected dependencies are initialised before the hook call — **no TDZ/runtime-order hazard**.

## 6. Video storage ownership

- Canonical key: **`theprams_demo_video_lessons`** (exact, unchanged).
- The Content domain now owns the key. It is defined once in `adminContentData.ts` as `VIDEO_LESSONS_STORAGE_KEY` and referenced from the hook.
- Read: `readStorageArray(VIDEO_LESSONS_STORAGE_KEY, defaultVideoLessons)` — same helper, same fallback argument.
- Write: `localStorage.setItem(VIDEO_LESSONS_STORAGE_KEY, JSON.stringify(nextVideos))` — same semantics.
- **No rename, no migration, no new Content key.** The admin registry stays at **13/13** `theprams_demo_*` keys.

### Preserved legacy read quirk (documented, NOT "fixed")

`readStorageArray` parses `localStorage.getItem(key) || '[]'`, so an **absent** key yields `[]` — the `defaultVideoLessons` fallback is only reached when the stored value is non-array or malformed. This is pre-existing shared behaviour (it also affects users/leads/etc.). B1.4D is decomposition, not feature work, so T5A **preserves it exactly** and does not change the shared reader. Consequence for reviewers: a fresh browser with no persisted key shows **0 seeded lessons** — identical to the pre-T5A monolith.

## 7. Save / delete / upload parity (preserved exactly)

| Operation | Preserved behaviour |
|---|---|
| **Save** (`saveVideoEditor`) | empty title → `notify('Judul video wajib diisi.')` and bail; trims title; `program` fallback `PROGRAMS[0].title`; `duration` fallback `'00:00'`; `thumbnail` fallback `defaultVideoLessons[0].thumbnail`; tags trimmed + `filter(Boolean)`; **replace by id OR prepend**; persists via the canonical writer; closes editor; `recordAudit('Content Library', 'Save Video Lesson', sanitized.title)`; `notify('Detail video berhasil disimpan.')`. |
| **Delete** (`deleteVideo`) | filters the demo list by id and `notify('Video "<title>" dihapus dari daftar demo.')`. **No confirmation dialog was invented**, and this is not a server delete. |
| **Upload** (`simulateVideoUpload`) | requires a title (blank → no-op); `idle → uploading`; progress restarts at `0`; `setInterval` increments by **5** every **100 ms**; at `>= 100` clears the interval, sets `completed`, and after **1500 ms** closes the modal, resets status to `idle` and resets the form via `createInitialVideoForm()`. |

### Upload is a DEMO simulation

Despite the UI copy ("Video File", "Start Upload", "ditambahkan ke database"), there is **no real upload** and **no File API persistence**. Selecting a file / pressing Start Upload only drives the demo progression in the hook — and it does **not** even append the video to `videoLessons`. T5A preserves this exactly and adds no real upload capability.

- **Editor dialog:** the row Edit action sets `editingVideo` to the correct record (prefill); **Batal** clears it (`editingVideo → null`).
- **Transient state (key parity check):** opening the editor for "TPA Penalaran Logis", navigating client-side to `/admin` and back to `/admin/studio/content`, left `editingVideo` **unchanged**; opening the upload modal across the same round-trip left `isUploadModalOpen = true`. A `window` marker survived both round-trips, proving **no page reload** — the state lives in the persistent `AdminDashboard`, exactly as the legacy monolith behaved.
- **T5B non-regression:** `/admin/studio/website` still renders the "Website Editor Panel" (plus "Editor Info Menarik" / "Literasi"), and `Content Management` is absent there.
- **Console: 0 errors, 0 warnings.**
- **Cleanup:** the seeded `theprams_demo_video_lessons` key was removed afterwards; only the pre-existing `theprams_demo_audit_events` key remained, and the page correctly returned to 0 seeded lessons. No persisted mutation was left behind.

**PARTIAL disclosure:** the agent browser tab is an **offscreen renderer** (`document.hidden === true`), so `requestAnimationFrame` is throttled and `motion`'s enter/exit animations never advance. As a result the **visual fade/scale completion** and the `AnimatePresence` **DOM removal** after closing a modal were **not** observable (state was read from the live React tree via the current fiber root, and initial animation frames remained stuck). The upload **progress ring animation** was likewise not watched frame-by-frame; the `idle → uploading → completed` progression and the `5 / 100 ms / 1500 ms` timings are asserted as a source contract in verifier section **AK**. Real-visual acceptance (animation completion, exact pixel targets) remains for B1.5/T10.
