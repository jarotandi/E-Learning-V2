## The primitive construction rule

Every primitive is built the same way, and the rule is the contract:

1. **Base appearance** is an inline `style` object whose values are read from
   `src/design-system/tokens/brand.ts` at render time. A primitive therefore
   cannot drift from the palette, because it contains no colour literal.
2. **State** (`:hover`, `:focus-visible`, `[aria-invalid]`,
   `[data-aksa-disabled]`) cannot be expressed in a React style object, so those
   rules live in `primitives.css`, scoped to `data-aksa-*` attributes, reading
   `var(--aksa-*)` custom properties that the component publishes.

Three alternatives were considered and rejected:

| Option | Why rejected |
|---|---|
| Inject a `<style>` element from JavaScript | This is B1.3 DEFECT-2. It mutated the document at runtime and hid a real layout value from the cascade. Repeating it would regress a decision the architect already made. |
| Tailwind arbitrary-value utilities (`hover:bg-[var(--x)]`) | Works, but the legacy `@theme` has no entry for `tealAccessible`, so a primitive's colours would come from Tailwind's generated CSS while its geometry came from tokens — splitting visual authority across two systems. |
| Add token aliases to `src/index.css` `@theme` | The brief forbids an `index.css` rewrite, and it would couple the new primitive layer to the file scheduled to shrink in B1.5. |

The stylesheet is a real, static, import-time file. Every rule in it is gated on
a `data-aksa-*` attribute, so it cannot restyle a single legacy component in
`src/components/`.

Verified in the built CSS (`dist/assets/index-DR9AAL8i.css`): all seven
`data-aksa-*` selector groups and the `prefers-reduced-motion` block are
present, and the rules contain no colour literal — only `var(--aksa-*)`.

## `primitives.css` is loaded from `src/main.tsx`

**This is the one change outside the brief's enumerated change areas**, and it
is called out here rather than buried.

`primitives.css` is imported from `src/main.tsx`, beside `index.css`, instead
of from `design-system/components/index.ts`.

- Keeping the barrel free of a `.css` import is what allows
  `scripts/verify-design-system.mjs` to import the real modules under plain
  Node and assert their actual exported API. A barrel that reaches for a
  stylesheet cannot be loaded that way — the check fails with
  `ERR_UNKNOWN_FILE_EXTENSION` before a single assertion runs.
- It follows the convention already in that file: global stylesheets are loaded
  once, at the entry point.
- The change is one import plus a comment. It alters no behaviour, and
  `src/index.css` is untouched.

The alternative — a JS-injected `<style>` or a per-call-site hex — was
rejected for the reasons in the table above.

## PublicHeader — every legacy capability preserved

`href` values come from `legacyViewToPath`, the existing single translation
layer. This file contains no route string of its own.

| Destination | Legacy label | Here | Canonical path |
|---|---|---|---|
| `landing` | Home | Home | `/` |
| `programs` | E-Learning Program | Program | `/programs` |
| `guestRegistration` | Tryout Gratis 🔥 | Tryout Gratis + "Baru" 🔥 badge | `/register/guest` |
| `blogListing` | Info Menarik | Info | `/blog` |
| `testimonials` | Testimoni | Testimoni | `/testimonials` |
| `login` | Masuk | Masuk | `/login` |
| `register` | Daftar | Daftar | `/register` |
| `dashboard` | Dashboard | Dashboard | `/app` |
| logout | Logout | Logout | `requestLogout` confirmation |

Guest handling is unchanged: `PublicLayout` still evaluates
`user?.id === 'u_guest' ? null : user`, and a guest therefore still sees
Masuk/Daftar rather than a profile.

### Labels were shortened, deliberately

The brief's inventory step (STEP 2) enumerates the legacy labels; its visual
target (STEP 4) specifies "Home / Program / Tryout Gratis / Info / Testimoni".
These conflict for two items, so the visible label follows STEP 4 and the full
legacy phrasing is kept as the accessible name. No descriptive text is lost,
and WCAG 2.5.3 (Label in Name) holds because the visible text is contained in
the accessible name: "Program" ⊂ "E-Learning Program", "Info" ⊂ "Info Menarik".

### Real links, router-backed navigation

Destinations are `<a href>` elements, so they keep link semantics, a
middle-click, and cmd/ctrl-click to open in a new tab. A plain left click is
delegated to the router-backed `setView`, because the legacy demo user lives in
React state and a real page load would drop it. Modified clicks and non-primary
buttons are explicitly passed through to the browser.

### Disclosure, not a menu

The signed-in popover is a disclosure (`aria-expanded` + `aria-controls`), not
`role="menu"`. A `role="menu"` obliges the author to implement the whole APG menu
keyboard model — arrow navigation, type-ahead, roving focus — which a two-item
popover does not need and would only half-implement.

## Defects found and fixed in place

### DEFECT-1 — no navigation at all between 768px and 1023px

The legacy header revealed the auth buttons from `md` (768px) but the nav links
only from `lg` (1024px), and the hamburger only *below* `md`. Between 768px and
1023px a visitor could sign in but could not navigate anywhere: the auth block
was visible, the nav links were hidden, and the hamburger was hidden too.

Fixed by using ONE breakpoint for both desktop clusters: full navigation at
`lg` and above, hamburger below it. Verified at a 1000px viewport — the exact
width that was previously dead.

Note this is the same class of defect as B1.3 DEFECT-3, found independently in a
different file.

### DEFECT-2 — the mobile drawer had no signed-in state

The legacy drawer always rendered "Masuk" / "Daftar", even when signed in. A
signed-in mobile user therefore had no route to the dashboard and no way to sign
out from public chrome — the only route to either was a full page load, which
drops the in-memory session.

The drawer now renders the same auth block as the desktop bar: Dashboard and
Logout when signed in, Masuk and Daftar otherwise. Verified in the browser.

### DEFECT-3 — four contrast violations in the public header

Measured, not assumed:

| Element | Pairing | Ratio | Verdict |
|---|---|---|---|
| "Daftar" label | white on `#009688` | 3.67:1 | **fails AA** |
| "Masuk" label | `#009688` on white | 3.67:1 | **fails AA** |
| Active nav link | `#009688` on white | 3.67:1 | **fails AA** |
| "Baru" badge | `text-red-500` on `bg-red-50`, 9px | ~3.9:1 | **fails AA** |

All corrected through the primitives. `brand.tealAccessible` (`#00796b`,
5.32:1) replaces `#009688` wherever text is involved; the badge uses the
design-system `Badge`, whose label is `brand.emerald` (9.15:1 on its surface).

`brand.teal` (`#009688`) is retained for the monogram tile, the focus ring,
borders, and icons — non-text use, where 3.67:1 is correct.

### DEFECT-4 — the profile popover had no keyboard or dismiss affordance

The legacy popover had no `aria-expanded`, no Escape handling, and no
outside-click dismissal. Fixed: `aria-expanded` + `aria-controls`, Escape
closes and returns focus to the trigger, outside pointer-down closes, and
`aria-label` is `Menu akun {name}` so the control's accessible name is the
account, not the word "Dashboard".

## Contrast audit of the primitive set

Every pairing below was computed, not assumed. AA for normal text is 4.5:1; for
large text and non-text UI boundaries it is 3:1.

### Badge — why every variant uses the same text colour

The obvious recipe — semantic hue text on its own soft surface — fails for this
palette:

| Text | On its soft surface | Verdict |
|---|---|---|
| `semantic.success` | `successSoft` | 3.32:1 fails |
| `semantic.warning` | `warningSoft` | 2.86:1 fails |
| `semantic.error` | `errorSoft` | 3.95:1 fails |
| `semantic.info` | `infoSoft` | 3.57:1 fails |
| `brand.gold` | `goldSoft` | 1.53:1 fails |

So `Badge` always uses `brand.emerald` for the label and carries the variant in
the background. Measured on every soft surface: 8.91 / 8.57 / 8.73 / 7.96 /
8.47 / 9.15 — all pass AA comfortably. Gold keeps its documented role: it is
the `planned` variant's *surface*, and it is never text.

### Button

| State | Fill | White text |
|---|---|---|
| primary | `brand.tealAccessible` | 5.32:1 AA |
| primary hover | `brand.tealActive` | 6.61:1 AA |
| secondary | `brand.emerald` | 9.72:1 AAA |
| danger | `semantic.error` | 4.83:1 AA |
| danger hover | `#b91c1c` | 6.47:1 AA |
| outline / ghost | transparent | 5.32:1 AA |

`primary` is `#00796b` and **never** `#009688`, as required.

### The control-boundary rule

`neutral.200` is 1.26:1 on white and `neutral.300` is 1.48:1, so neither may
bound a control whose state must be identified (WCAG 1.4.11). `Input` therefore
uses `neutral.500` (4.74:1) at rest, `tealAccessible` (5.32:1) on focus, and
`semantic.error` (4.83:1) when invalid.

Decoration is held to a different standard: a `Card` border and `Table` cell
dividers are not state indicators, so `neutral.200` is correct there, and the
`Card` `interactive` variant moves to `tealAccessible` precisely because that
card *is* a control.

### Focus ring

`2px solid #009688` with `2px` offset, read from the `focusRing` token. Teal is
a boundary, not text, so 3.67:1 clears the 3:1 requirement.

Verified in the browser with a real Tab keypress: `:focus-visible` matches, and
the computed style is `outline: 2px solid rgb(0,150,136)` with
`outline-offset: 2px`.

### Disabled controls

`neutral.500` on `neutral.200` does not reach 4.5:1. WCAG 1.4.3 explicitly
exempts inactive user-interface components, so this is intentional and
documented in `Button.tsx`: a disabled control that stays fully legible competes
with the enabled one it is telling you not to use.

### Token discrepancy found, deliberately not corrected

`src/design-system/tokens/brand.ts` records
`contrast.emeraldOnWhite: 8.9`. The measured value is **9.72:1**. Reported
rather than silently edited: the token file is B1.1-era authority and changing a
sealed-era value belongs to its own correction pass, as B1.3R1 did for
`routePaths.ts`. No behaviour depends on it.

## Design decisions the architect should review

### No `loading` prop on `Button`

The brief allowed `loading` "only if it can be implemented without fake async
behaviour". It cannot: a presentational primitive has no request to await, so
the flag would be a lie waiting to be wired up. Omitted deliberately, and
documented at the call site in `Button.tsx`.

### Exported variant tuples are `Object.freeze`d

`as const` gives a readonly *type*; the array is still mutable at runtime, so one
caller doing `BUTTON_VARIANTS.push(...)` would silently corrupt the contract for
every other caller. `Object.freeze` makes the guarantee real, and
`scripts/verify-design-system.mjs` asserts it. This was found by the check
failing, not by inspection.

### Header height stays 80px, and `zIndex.nav` is not used

Both are deliberate deviations from a token reading, each backed by evidence.

- **Height.** `layout.nav.headerHeight` is 4rem. `LandingPage` and
  `TestimonialsPage` hard-code `pt-20` (80px) to clear the fixed header, so a
  64px header would open a 16px gap above the hero on every public page. The
  token remains the learner/studio shell height; aligning the public header with
  it is B1.5 visual acceptance. Measured in the browser: 81px rendered (80 + 1px
  border).
- **Stacking.** `ProgramDetailPage`'s fixed bottom bar already sits at `z-50`.
  Raising the header to `zIndex.nav` (1000) would invert a relationship the
  legacy pages rely on. `z-50` is kept. The token *is* used for the popover,
  where it is safe: the header is `position: fixed` with a non-auto z-index, so
  it establishes a stacking context and the popover cannot escape above it.

### `Navbar` is retained, deprecated — not deleted

STEP 5 permits deletion once every behaviour is proven migrated. Migration is
proven for the eight public destinations, the mobile drawer, and the signed-in
Dashboard/Logout flow. What is **not** proven is visual-parity acceptance, which
is B1.5 work and has not run. The file costs nothing at runtime and is the only
record of the legacy inventory, including the two defects corrected above.
Removal is a B1.5 candidate once visual acceptance passes.

Proof that nothing imports it — a repository-wide search across `src/`,
`scripts/`, `docs/`, and `index.html` returned no `import` statement for the
module. The remaining occurrences of the identifier are prose in
`app/router/*` and `app/layouts/*`, the `showsLegacyNavbar` /
`NAVBAR_HIDDEN_LEGACY_VIEWS` chrome-visibility rule in `legacyViewRoutes.ts`
(unchanged and still live), and the word "navbar" inside `AdminDashboard` CMS
copy. Confirmed absent from the production bundle.
