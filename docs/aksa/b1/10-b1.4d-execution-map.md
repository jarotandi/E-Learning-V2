### Rationale for T8 (Finance isolation)

Finance is isolated in **T8** because it owns the most complex and coupled subdomain:

- 7 finance subviews (`payments`, `inputs`, `realization`, `assets`, `accounting`, `reports`, `audit`)
- Transactions, payment proofs, finance entries, realizations, assets
- Accounting derivations and ledger construction
- Reports and audit + notification integration
- Multiple localStorage keys (13 total; finance dominates several)
- Many cross-dependencies with programs, leads, payments

Isolating finance to T8 reduces coupling risk and allows earlier extraction of simpler domains.

## State-Preservation Architecture (Accepted)

T1 establishes a **single persistent route branch** for admin:

```text
<Route element={<AdminLayout />}>
  <Route path="/admin/*" element={<AdminRouteBoundary />} />
</Route>
```

- Admin child navigation does **NOT** use 13 independent `<Route>` elements. All canonical admin URLs share one mounted boundary.
- For canonical tab URLs, `pathToLegacyView(path)` returns `'admin'`, so `currentView` remains `'admin'`.
- `LegacyRouteBridge` keeps `key={currentView}` (not `location.pathname`). `AdminDashboard`, `LegacyRouteBridge`, `AdminRouteBoundary` are **not** keyed by pathname.
- `AdminShellContext` (mounted in `AdminLayout`) derives `activeTab` from `adminPathToTab(location.pathname)`; `AdminDashboard` consumes it and keeps a thin `navigateToTab` shim (`setActiveTab`) to preserve all existing call sites. (Before T2 the derivation lived in `AdminDashboard`.)
- **SOURCE CONTRACT only.** Runtime transient-state persistence (form drafts, editing records, selected rows, open modals, finance subview, filters, upload progress) is **NOT VERIFIED IN BROWSER** by T1. T2 adds a partial browser smoke (search draft survives tab switches) — see the T2 gates section and `docs/aksa/b1/11-b1.4d-t2-admin-shell.md`.

## Anti-Monolith Rule

**B1.4D MUST NOT** become:

```
AdminDashboard.tsx 402 KB → AdminWorkspacePage.tsx ~400 KB
```

Target architecture:

- `AdminDashboard.tsx` → eventually a **thin compatibility wrapper** (preserves exact legacy prop contract).
- `AdminWorkspacePage.tsx` → a **small composition/orchestration surface only**.
- Domain behavior/state moves incrementally into coherent **domain components**, **domain hooks**, **pure models**, and **shared utilities**.
- Only state genuinely shared across domains is lifted upward.

The pure routing contract (`src/features/admin/shell/adminWorkspaceModel.ts`) is intentionally small and pure (no React/router/localStorage).

### T2 Outcome (as built)

| Item | Before T2 | After T2 |
|---|---|---|
| Shell owner | `AdminDashboard` (6,498-line monolith) | `AdminLayout` (`/admin/*` persistent route element) |

| Active tab | `adminPathToTab` in `AdminDashboard` | `adminPathToTab` in `AdminShellContext` |
| Navigation adapter | `navigate(adminTabToPath(tab))` in dashboard | `navigateToTab(tab)` from shell; dashboard keeps a `setActiveTab` shim |
| Header | sticky legacy header in dashboard | non-sticky **content toolbar** in dashboard (Search + Bell) + **shell top bar** in layout |
| Mobile navigation | none (sidebar `hidden lg:flex`) | drawer owned by `AdminLayout` |
| Logout | sidebar button → `logout` prop | `AdminLayout` → `requestLogout` (LegacyAppStateProvider) |
| Role matrix in shell | n/a | `ADMIN_ROLE_PERMISSIONS` / `isAdminTabAllowed` from the pure model |

New files:

- `src/features/admin/shell/AdminShellContext.tsx` — shell provider + context.
- `src/features/admin/shell/adminNavigation.ts` — 13-item navigation registry (labels/icons, exact legacy order).

`AdminShellContext` owns **only** shell-level state: `adminRole`, `activeTab` (URL-derived), `navigateToTab`, `isTabAllowed`, `allowedTabs`, `logout`. No business-domain state is lifted.

### Disallowed direct URL — UI presentation redirect

When a non-Super-Admin role lands on a tab URL it is not allowed to see, the shell corrects presentation with `navigate('/admin', { replace: true })`. This is **UI presentation only** — no 403, no auth claim. SEC-P1-03 remains OPEN (B2).

### Chrome moved to AdminLayout

- AKSA admin branding
- Sidebar navigation (desktop)
- Mobile navigation/drawer (to be established/owned by shell)
- Role switcher
- Current admin identity display
- Logout action (adapter)
- Shell/header
- Active route navigation (URL-driven; consumes canonical admin paths)

### What T2 does NOT extract

- Users business UI, questions, content, website, reviews, programs, leads, marketing, finance, analytics, settings business content
- `AdminDashboard` remains the business-content monolith temporarily, but becomes **content-only** (no duplicate shell)

### T2 State Ownership Decision

- `adminRole` (and `setAdminRole`) must move to **shell-level ownership** in T2 because it controls navigation visibility.
- Use a narrowly scoped `AdminShellContext` (or equivalent) owning only: `adminRole`, `setAdminRole`, allowed-nav derivation, logout adapter if needed by shell.
- **Do NOT** place the 70+ domain states into shell context.
- Role switch semantics remain: role change → navigate to `/admin` (overview). UI filtering only.
